# View contracts

A view contract prevents several sections from competing to explain the same thing.

For every view write:

- **Name**
- **Primary user question**
- **Journey stage**
- **Inputs**
- **Transformation**
- **Output**
- **What it deliberately does not answer**
- **Relationship to other views**
- **Default visibility**
- **Role visibility**

## Strong contracts

### Source / voice
Question: **What does this source say, in its own context?**

Owns:
- source-specific narrative
- primary passages
- source-specific commentary
- provenance

Does not own:
- cross-source conclusions
- final comparison
- global synthesis

### Comparison
Question: **Where do the sources agree, differ, or leave gaps?**

Owns:
- shared questions/facets
- side-by-side answers
- agreement/conflict/gap structure

Does not own:
- long source essays
- a rewritten combined narrative

### Synthesis
Question: **What higher-order understanding follows from the evidence as a whole?**

Owns only conclusions that require multiple inputs:
- consensus
- irreconcilable conflict
- uncertainty
- patterns
- implications
- carefully scoped combined conclusions

A synthesis is not justified if it merely restates every source in sequence.

### Evidence / verify
Question: **Why should I trust this statement?**

Owns:
- citation
- quotation/reference
- provenance
- confidence/strength
- trace back to source

Default visibility is usually compact or on-demand unless verification is the
primary task.

## Collision test

Two views collide when they share:
- the same question
- the same inputs
- the same stage
- low transformation between them

Collision verdicts:
- `MERGE`
- `MAKE_ONE_A_LENS`
- `REMOVE`
- `DIFFERENTIATE_CONTRACT`

Do not solve collision by giving the two views different colors or headings.
